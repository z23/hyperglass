<Callout type="warning">
    **A reverse proxy is required for production.** hyperglass should never be exposed directly to
    the internet on its application port. Always put [Caddy](https://caddyserver.com) (recommended),
    [NGINX](https://www.nginx.com), [Apache](https://httpd.apache.org), or another reverse proxy in
    front of it, and bind hyperglass to localhost (or a private network) only.
</Callout>

## Why a reverse proxy is required

hyperglass is an unauthenticated looking glass: each query can open a live session to a network
device. A reverse proxy gives you:

| Concern | What the proxy provides |
| --- | --- |
| **TLS** | HTTPS termination (e.g. automatic Let's Encrypt with Caddy). |
| **Client identity** | A single hop that overwrites `X-Forwarded-For`. The rate limiter uses the ASGI client address resolved by Uvicorn, not raw request headers. Uvicorn must trust only your sanitizing proxy. |
| **Attack surface** | Keep the uvicorn workers off the public internet; only the proxy listens on `:443` / `:80`. |

The stock `compose.yaml` publishes hyperglass on `127.0.0.1` only so it is not world-reachable
by default. Point Caddy (or another proxy) at that local port.

Set `FORWARDED_ALLOW_IPS` to the exact proxy peer address seen by Uvicorn (its
default is `127.0.0.1`). Docker and IPv6 loopback deployments may use a different
peer address. Do not use `*` or trust public client addresses. An untrusted proxy
will cause its clients to share one rate-limit budget; an overly broad trust list
can let clients spoof their identity. Check this setting against your actual
network path before rollout, including any CDN or load balancer in front.

Query admission requires Redis, including permission to run Lua scripts (`EVAL`).
Redis errors reject the query instead of bypassing the limiter. Counters use a new
key format, so each client receives a fresh budget once when upgrading from the
previous limiter. Avoid a prolonged rollout with mixed old and new workers.

The query-output cache also uses a new versioned key so responses cached before
the plugin-policy fixes are not returned. Expect a temporary increase in device
queries while the new cache warms. Existing keys are left to expire; no database
flush is required. Older workers must be drained because they still serve the
old output cache and use the old limiter.

[Caddy](https://caddyserver.com) is recommended, but any reverse proxy ([NGINX](https://www.nginx.com), [Apache2](https://httpd.apache.org)) will work.

## Caddy

<Cards>
    <Cards.Card
        title="Install Caddy"
        target="_blank"
        href="https://caddyserver.com/docs/install"
        arrow
    />
</Cards>

```shell copy
cp /opt/hyperglass/.samples/Caddyfile /etc/caddy/Caddyfile
```

Change the `lg.example.com` and `person@example.com` values to match your hyperglass FQDN and email address (the email address is for automatic SSL certificate generation via Let's Encrypt).

Ensure the `reverse_proxy` target matches where hyperglass listens (default `localhost:8001`).

Caddy's `reverse_proxy` sets `X-Forwarded-For` and related headers from the connecting client. Do
**not** forward client-supplied `X-Forwarded-For` from an untrusted hop in front of Caddy without
stripping or overwriting it first.

<Callout type="info">
    If you prefer to use other Let's Encrypt validation methods or your own SSL certificate, modify
    your `/etc/hyperglass/Caddyfile` in accordance with the [Caddy
    docs](https://caddyserver.com/docs/caddyfile-tutorial).
</Callout>

Restart the Caddy service: `systemctl restart caddy{:shell}`

## NGINX

```shell copy
cp /opt/hyperglass/.samples/hyperglass.nginx /etc/nginx/sites-available/hyperglass
ln -s /etc/nginx/sites-available/hyperglass /etc/nginx/sites-enabled/hyperglass
```

Change the `lg.example.com` value to match your hyperglass FQDN.

Change the `<path to cert chain>` and `<path to key>` values to match the path to your certificate and private key files.

Configure NGINX to set (not append blindly) the forwarding headers, for example:

```nginx
proxy_set_header Host $host;
proxy_set_header X-Real-IP $remote_addr;
proxy_set_header X-Forwarded-For $remote_addr;
proxy_set_header X-Forwarded-Proto $scheme;
```

Using `$remote_addr` (the peer that connected to NGINX) avoids clients spoofing their own IP into
the rate-limit bucket when NGINX is the only public hop.
